# 薬局システムのドメイン候補一覧

利用先の想定はレセコン・電子薬歴の一体型クラウドシステム。両者は業務上の機能区分として整理し、別製品連携を必須としない。

目的: 薬歴などのアプリから再利用できる薬局ドメインモデルを作る。以下はモデルに含める業務の候補であり、すべてを最初に実装するという合意ではない。

将来の対象は薬局業務全体。在宅、算定・会計・請求、調達・在庫、OTCを含める。各候補の責務・分割と実装順序は引き続き検討する。

対象外: 給与計算、人事評価、企業の財務会計。資格・配属・勤務、窓口会計・請求は対象に含める。

状態: 相談用。まず業務の責務と対象を整理する。各行は独立した実装コンテキストを確定するものではない。DDD・純粋計算等の実装方式、共通IDの配置は後で決める。

レイヤーは文書を探すための業務分類であり、プログラムの依存方向を表すものではない。

業務の整理は **レセコン入力 → 服薬指導 → 薬歴記載 → フォローアップ** を軸に進める。具体的な受け渡しは [業務フロー](03-clinical/workflow.md) を参照。業務の順番と、責務による分類を区別する。

## 1. 組織・基盤

文書: [組織・基盤](01-organization/README.md)

| 候補 | 主な責務 | 境界の論点 |
| --- | --- | --- |
| 法人・法人間関係 (`corporate`) | 法人（持株会社等を含む）の識別、親子関係と履歴。個人開設者の正本の置き場所は未決 | 法人＝テナント。企業グループの階層は設けない。提携・FC・関連会社の関係管理は現段階の対象外。報酬上の判定とは区別 |
| 店舗 (`store`) | 店舗、拠点、屋号、開設者（法人・個人）との関係、営業状態、許可・指定の履歴 | 店舗IDと所在地・許可・外部コードを区別 |
| スタッフ (`staff`) | 職員、資格、所属・配属、応援、勤務、管理者の就任 | 兼務等の条件は適用規定と例外を確認。常勤換算は目的別の算定との境界を検討 |
| 施設基準・届出 (`facility_compliance`) | 届出、適用期間、根拠実績、報告 | 報酬計算に渡す条件と元実績の正本を区別 |
| 品質・インシデント (`quality`) | 店舗からの事故・ヒヤリハットの起票・提出、開設者（法人・個人）による受付・調査・対応・改善・完了の管理 | 起票店舗と管理主体を保持し、調剤等の業務記録・閲覧権限と区別 |
| テナント・アクセス管理 (`tenant_access`) | 開設主体単位のデータ分離（法人または個人開設者＝テナント）、利用者と権限、承継・移行 | 企業所属と薬歴閲覧を自動的に同一視しない。技術基盤との実装上の分担は未定 |

## 3. 患者・臨床・ケア

文書: [患者・臨床・ケア](03-clinical/README.md)

| 候補 | 主な責務 | 境界の論点 |
| --- | --- | --- |
| 患者 (`patient`) | 患者の識別、基本情報、アレルギー・副作用等の臨床情報、同意 | 同一患者の照合、情報の出所・有効時点。相互作用等の判定は処方監査と区別 |
| 保険・公費等 (`coverage`) | 医療・介護保険、公費、資格確認結果、適用期間 | 処方箋の記載内容と確認済み資格を区別 |
| 処方箋・処方内容 (`prescription`) | 原記載、発行情報、患者・処方者、Rp、薬剤明細、用法・用量・単位・日数、受付、版・変更履歴 | 原記載、確認後の指示、実際の調剤を区別。リフィル・分割の受付と実施の対応を検討 |
| 受付・処方入力 (`reception_entry`) | 一体型の患者登録・処方入力、受付と患者・処方の対応 | 内部では情報を直接共有。外部NSIPSの変換・受信履歴は連携側で扱う |
| 処方監査・疑義照会 (`prescription_review`) | 処方の評価、照会、回答、変更の根拠 | 処方内容の正本・版管理は処方箋側。評価結果から変更をどう確定するかを検討 |
| 調剤・鑑査 (`dispensing`) | 調製、薬剤・数量の実績、最終鑑査、調剤録 | 処方指示と実施結果、在庫払出を対応づける |
| 服薬指導・交付 (`medication_counseling`) | 説明、理解の確認、薬剤交付、実施者・実施時点 | 実施業務と薬歴への記録の責任を整理 |
| 在宅 (`home_care`) | 契約・指示、計画、訪問予定・実施、関係者への報告 | 訪問の実施と薬歴・算定の責務を区別 |
| 受付・相談・フォローアップのイベント (`care_event`) | 内部の受付情報共有または外部NSIPS取込による処方箋受付、各種相談・フォローアップ等の出来事、イベント間の関連、開設者ごとの独自種別 | イベントを先行作成し後から記録を紐づける。受付イベントは処方箋との対応を持ち、記載内容は薬歴等の記録側が持つ |
| 薬歴記載 (`medication_history`) | SOAP・病歴等をまとめた薬歴記載、下書き・確認・確定・訂正。一イベントに複数の記載を紐づけられる | SOAPは表現形式の候補。指導やフォローアップの実施と記録を対応づける |
| フォローアップ (`follow_up`) | 対象・目的・予定、連絡・確認、服薬状況等の評価、必要な対応、次回計画 | 活動の進行を管理し、結果は薬歴に関連づける。連絡不能と完了を区別 |

## 一覧から決めること

1. 各候補を対象に含めるか、責務に抜け・重複がないか。
2. 誰が何を開始し、どの結果で終わる業務か。
3. どの領域が記録の正本を持ち、他領域へ何を渡すか。
4. 通常の流れと、変更・取消・承継時の関係をどう扱うか。

IDは意味と所有者を各領域で整理してから共有を判断する。制度条件は一次資料・該当箇所・適用日を確認して記載する。

## レイヤーをまたぐ外部連携

NSIPSは外部連携用とし、一体型内部では情報を直接共有する。外部レセコン等の取込と、レセコン機能から他社の分包機等への送信を扱う。製品ごとの変換・送受信の責務と、患者・処方・調剤等の業務ルールを分ける。詳細は [内部と外部連携の境界](external-integration.md) を参照。

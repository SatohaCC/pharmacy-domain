# React Effectの要否判断

## 基準

Effectを削減すること自体を目的にしない。処理の実行理由とstateの所有者を明確にし、必要な外部同期を維持する。以下は記事の判断基準を実務へ適用するための指針であり、記事の転載ではない。

## 処理の置き場所を選ぶ

対象のEffect、その依存値、呼び出し元を読み、「何が起きたから実行するのか」を確認する。

| 実行理由・対象 | 第一候補 |
|---|---|
| 現在のprops/stateから表示値を求める | レンダー時の純粋な計算 |
| 送信・購入・選択など特定の操作に応答する | イベントハンドラ。複数の入口は共通関数を呼ぶ |
| 表示中の条件に合わせて接続や外部状態を保つ | Effect、または既存ライブラリの同期機構 |
| 外部ストアのスナップショットを購読する | 既存の公式Hook、またはuseSyncExternalStore |
| アプリ起動時の初期化 | 既存の起動境界。マウントと起動を区別する |

POST/GETというメソッドや依存配列の長さだけで分類しない。URLや戻る・進むでも更新される検索条件は、特定の入力イベント以外からも変化する。画面表示の計測にも外部同期としての理由がある。

## 置き換えの判断

- **派生値**: 計算結果をstateへ複製する前に、元データから直接算出する。高価な純粋計算だけ、計測結果と既存の最適化環境を踏まえてuseMemoを検討する。メモ化を正しさの条件にしない。
- **対象変更時のリセット**: 全体を作り直す要件なら安定した識別子をkeyに使える。一部だけの調整なら、保存する情報を最小化し、残りを導出できるか検討する。必要な場合に限り、前回値との差を条件に同じコンポーネントのstateをレンダー中に調整する。無条件の更新や、レンダー中の親更新・外部副作用を持ち込まない。
- **操作からの更新**: 次の値をイベント内で計算し、必要なstate更新と通知をそこで行う。setterの直後も現在の変数は更新前のスナップショットなので、必要ならnext値を明示する。updaterやreducerに通知・通信を入れない。
- **親子の同期**: 同じ情報を双方で保持する必要を確認する。親が所有してpropsで渡す構成や、同じイベントでのコールバック通知を検討する。単に子のデータを親へ中継するEffectを増やさない。
- **Effectの連鎖**: 純粋な状態遷移は同じイベントや既存のreducerへまとめる。一方、前の選択に依存するネットワーク取得などは外部同期として判断する。
- **初期化**: 空の依存配列を「一度だけ」の保証とみなさない。Strict Modeを無効化したり、refで再実行を隠したりして解決しない。起動境界へ移す場合もSSR、ブラウザAPIの有無、import時の副作用、再マウントを確認する。

## 必要な同期を維持する

既存のフレームワーク、データ取得・キャッシュ・購読APIを優先し、このSkillの適用だけを理由に取得方式やライブラリを変更しない。Hookへの抽出だけではEffectの必要性や競合は解決しない。

残すEffectでは同期対象、開始条件、解除処理を説明できるようにする。依存値を隠したりlintを抑制して実行回数を調整しない。購読・接続は再設定と解除が対応しているか確認する。外部ストアではsubscribe、snapshot、SSR時の初期値の契約を確認する。

Effectで取得する場合は、古い応答の無視や対応APIのキャンセルで競合を防ぎ、成功・失敗・loadingの更新すべてが古い要求に上書きされないようにする。

## 挙動の保全と検証

リファクタリング前に、次の変更が仕様に合うか確認する。

- 配列が変わるたびの選択解除と、選択IDが存在する限りの維持は異なる。
- keyの変更は子孫の入力・フォーカス・接続も作り直す。
- Effectからイベントへ移した通知は、初回表示や外部更新時には発生しなくなる。

依頼がレビューのみならコードを編集しない。具体的な問題、実行理由、最小の代案を示し、適切なEffectには変更不要と判断してよい。実装依頼では対象範囲の既存契約を保つ。

変更に応じて、初回表示、props変更、連続操作、再マウント、応答順の逆転など、影響する振る舞いを既存の検証手段で確認する。Effectの数やHookの名前自体をテストしない。結果は変更理由と実施した検証、未確認事項を簡潔に伝える。

# コードレビュー

実装ロジックのバグ・エッジケース・セキュリティ・設計契約の違反を、実装時とは独立した視点で検出する。リンターで機械的に縛れるかどうかの判断は [git-commit Skill](../git-commit/SKILL.md) 側で行う。

## 対象差分の決め方

- **コミット前レビュー（`git-commit` Skill から実行）**: ステージ済み差分（`git diff --cached`）を対象とする。
- **PR 前レビュー・明示依頼**: 依頼された差分（例: `git diff main...HEAD`、`git diff`、指定ファイル）を対象とする。

## 独立レビューの原則と軽量化ルール

- **コード・スクリプト・設定・テスト・フックに変更がある場合**: 確証バイアスを避けるため、実装コンテキストを持たない**読み取り専用サブエージェント**（`research` 等）を起動し、対象差分と必要最小限の周辺ファイルだけを参照してレビューさせる。
- **ドキュメント・コメント・フォーマット・ロックファイルのみの軽微な変更の場合**: サブエージェントは起動せず、差分をインラインで目視確認して完了してよい。
- **同一差分の二重実行防止**: 同一のステージ済み差分に対して直前にレビュー完了済みで追加変更がない場合は、再実行しない。
- **トークン節約**: 会話履歴全文や無関係なファイルは渡さない。変更されたファイル、呼び出し元、関連する契約・テストに絞って確認する。

## レビュー観点

`pnpm check`（Biome / Ruff / mypy / `import-linter` / `check:paths`）等の既存ツールで機械検出できる項目は繰り返さず、静的ツールが拾えない観点に集中する。

1. **ロジック・エッジケース・境界値**
   - 条件分岐・早期 return による後続処理の取りこぼし
   - 正規表現のグループ化漏れ・優先順位・エスケープ漏れ・部分一致による誤判定
   - `null` / `undefined` / 空文字 / 空配列 / 初期状態（初回コミットやキャッシュ未作成等）
   - 状態同期の入力経路網羅（`useState(initial*)` や `window.history` / `popstate` を含む場合、初回表示・画面操作・履歴遷移・同一ルートへのクライアント遷移 `<Link>` / `router.push` の全経路で状態がズレないか）
   - Windows / Linux 差異（パス区切り、改行コード、ファイル権限、シェル引数エスケープ）
2. **セキュリティ・安全性**
   - コマンドインジェクション・パストラバーサル・未検証入力の危険な利用
   - 秘密情報の混入、意図しないファイル削除・破壊的操作
3. **リポジトリ規約・契約整合性**
   - コメント・docstring が日本語か（[コーディング規約](../../rules/coding-style.md)）
   - Backend の責務分離・設定一元化（[Backend 設計ルール](../../rules/backend-architecture.md)）
   - Frontend 共有 UI の移植性（ドメイン文言・外部状態の混入等）（[Frontend 共有 UI ルール](../../rules/frontend-shared-ui.md)）
   - Frontend のレイアウト契約・URL 状態同期（[Frontend App Router ルール](../../rules/frontend-app-router.md)）
   - 共通ファイル（`layout.tsx`・共有フック・共通部品等）で契約を追加・変更した場合、差分に含まれていない全ルート（`app/**/page.tsx` 等）や呼び出し元が契約を満たしているか
   - モジュール間インターフェース・API スキーマ・フック入出力契約の整合性
   - 対象 Issue がある場合は、差分が担当範囲と受入条件に合っているか、報告された検証結果で各条件を判断できるかを照合する。確認できていない条件と理由はレビュー結果に残す。
4. **テストの回帰検出力**
   - 新規ロジックや修正バグの分岐・失敗系がテストで実際に検証されているか
   - 実装が壊れても通ってしまう弱いアサーションや過剰モックになっていないか

## 重要度分類と対応ルール

- **`[Blocking]`（修正必須）**: 実バグ、エッジケースによる誤動作、セキュリティ問題、明確な契約・規約違反、回帰を防げないテストの抜け。
  - コミット前レビューで検出した場合は修正し、関連するテスト・静的検査を再実行したうえで再ステージ（`git add`）する。
  - 修正後の再確認は修正差分に絞り、軽微な好みで無限ループしない。
- **`[Non-blocking]`（参考メモのみ）**: 命名の好み、今回変更範囲外の既存負債、任意のリファクタ提案。
  - コミットは止めず、必要であれば要約メモのみ残す。

## 出力フォーマット

指摘は箇条書きで簡潔に出力する。Blocking の指摘がなければ `Blocking 指摘なし` と明記する。未確認の受入条件があれば、条件と理由を併記する。

```text
- [Blocking|Non-blocking] <ファイルパス>:<行番号> — <不具合シナリオまたは違反内容> / 修正方針: <簡潔な案>
```

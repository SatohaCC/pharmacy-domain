# Git コミットワークフロー

用途に応じて以下のように適用する。

- **コミットメッセージ案の作成・修正のみ**: 「Conventional Commits 1.0.0（日本語）」のみ適用する（コードレビュー・リンター化判断レビュー・`mark-reviewed` は不要）。
- **`git commit` を実行する場合**: 以下の手順 1〜5 を順に実行する。

## トークン節約の原則（リンター化判断レビュー）

- 参照するのは **ステージ済み差分（`git diff --cached`）** と **集計済みサマリー（`.cache/lint-review/failure-summary.md`）** のみとする。
- `.cache/agent-failures/*.jsonl` の生ログや会話トランスクリプト全文は読み込まない。

## 失敗記録の仕組み（実装中の運用）

- **自動記録**: `PostToolUse` フックが `run_command` / `edit_file` / `write_file` の失敗を自動記録する（`exit status 1` 等の簡略エラー時はトランスクリプトの対象ステップから具体的なエラー行を抽出し、コマンド表記の違いを吸収してエラー原因ごとに集約する）。
- **明示記録（任意）**: ツールエラーにならない手戻り（レビュー指摘での修正、バックグラウンド実行の失敗、ロジックの見直し等）で再発防止を検討したいものは、実装中に以下で記録できる：
  ```powershell
  node scripts/lint-review-hook.mts record-failure --reason "<原因>" --target "<対象ファイルやコマンド>"
  ```

## 手順（コミット実行時）

### 1. 変更内容と検査の確認

- `git status` と `git diff --cached` でステージ済みの内容を確認し、依頼外の変更や不要ファイル（`.venv`、キャッシュ、実行ログ、ローカルの絶対パス等）を混ぜない。
- コミット前に `pnpm check:paths` および関連する lint / 型チェック / テストが通過していることを確認する。

### 2. コミット前コードレビュー

- [code-review Skill](../code-review/SKILL.md) に従い、ステージ済み差分（`git diff --cached`）をレビューする（同一のステージ済み差分で直前に完了済みなら再実行不要）。対象 Issue がある場合は、その参照先、担当する受入条件、実行した検証と結果、未確認の範囲と理由を差分と一緒に渡す。
- レビュー指摘による手戻りのうち今後の再発防止でリンター化を検討したいものは、`record-failure` で記録してから手順 3 へ進む。

### 3. リンター化判断レビューと確認済みマーク

コードの品質や規約違反を再発させないため、可能な限りリンターで機械的に縛れるかを確認する。一方で、ルール化・静的判定が難しい内容まで無理に縛らず、判断結果のみを残してそのままコミットへ進む。

1. **差分と 2 回以上の失敗記録を確認する**
   - `git diff --cached` で前回コミットからの変更内容を確認する。
   - `.cache/lint-review/failure-summary.md` を読み、実装中に 2 回以上繰り返された失敗パターンを確認する。
   - ネットワーク断・OS 権限エラー・一時的なプロセス競合などの環境要因、および単発のタイポはリンター候補から除外する。
2. **リンターで縛れるか 3 条件で判定する**
   - **静的判定性**: AST・import グラフ・型・命名・設定値だけで機械的に判定できるか。
   - **低誤検知**: 偽陽性が少なく、`biome-ignore` や `# noqa` などの抑制コメントを増やさずに済むか。
   - **費用対効果**: 実装・維持コストに対して今後の再発防止効果が見合うか。
3. **リンター化できる場合の優先順位**
   1. **Biome 設定**（`frontend/biome.json` の推奨ルール追加、`noRestrictedImports`、`noRestrictedGlobals`）
   2. **Ruff 設定**（`backend/pyproject.toml` のルール追加、`TID251` 禁止 API 追加）
   3. **`import-linter` 契約**（`backend/pyproject.toml` の `layers` / `forbidden` 契約）
   4. **Biome GritQL プラグイン**（`frontend/config/*.grit` によるプロジェクト固有 AST 制限）
   5. **軽量検査スクリプト**（`scripts/check-*.mts` + ルート `package.json` の `check` 組み込み）
   - 数行の設定追記で済むものはこの場で追加・`pnpm check` 確認のうえ `git add` する。
   - 大規模な独自リンター実装が必要な場合は、その場で無理に抱え込まず別 Issue / タスク候補として報告し、今回の変更自体はそのままコミットする。
4. **ルール化できない場合**
   - 文脈依存の設計判断、自然言語表現、テストケースの網羅性など静的に縛れない項目は無理にリンター化せず、判断理由だけ整理してそのままコミットを進める。
5. **確認完了をマークする**
   - 追加変更があればステージ（`git add`）したうえで、以下を実行して確認済みマーカーを記録する：
     ```powershell
     node scripts/lint-review-hook.mts mark-reviewed --note "<判断結果の要約>"
     ```
   - `PreToolUse` フックはコマンド実行前に評価されるため、`mark-reviewed` と `git commit` を同一コマンドで連結せず、別々のコマンドとして順に実行する。

### 4. コミットメッセージ作成（Conventional Commits 1.0.0・日本語）

「Conventional Commits 1.0.0（日本語）」に従い、ステージ済み差分と一致するメッセージを作成する。

### 5. コミット実行

確認済みマーカー記録後に `git commit` を実行する（フックで一時停止された場合は、手順 2・3 の確認と `mark-reviewed` 完了後に元の `git commit` を再実行する）。

## Conventional Commits 1.0.0（日本語）

コミットに含める差分を確認し、変更の目的に合う型を選ぶ。実際にコミットする直前は `git diff --cached` でステージ済みの内容を確認し、メッセージが差分と一致することを確かめる。

### タイトル

```text
<type>[(<scope>)][!]: <日本語の要約>
```

- 新機能は `feat`、バグ修正は `fix` を使う。その他の変更には `docs`、`refactor`、`test`、`ci`、`build`、`perf`、`style`、`chore` などから内容に合う型を選ぶ。既存の変更を取り消す場合は `revert` を使える。
- スコープは任意。対象が明確な場合に、コードベースの領域を表す名詞を括弧で囲む。例は `fix(ui): ステータス更新時の表示を修正`。
- 半角のコロンとスペースに続けて、変更を短い日本語で要約する。例は `chore: 初期テンプレートを整備`。

### 本文とフッター

- 本文は任意。タイトルの後に空行を入れ、変更理由や補足を日本語で書く。メッセージにはローカルの絶対パスや秘密情報を含めない。
- フッターは任意。タイトルまたは本文の後に空行を入れ、`Token: 値` または `Token #値` の形式で書く。複数語のトークンは `Reviewed-by` のようにハイフンでつなぐ。破壊的変更の `BREAKING CHANGE` には空白が含まれる。
- 破壊的変更はコロンの直前の `!`、または `BREAKING CHANGE: <日本語の説明>` フッターで明示する。`!` のみを使う場合は、タイトルで破壊的変更の内容がわかるようにする。移行手順が必要ならフッターで説明する。

```text
refactor(api)!: 旧形式の認証ヘッダーを廃止

BREAKING CHANGE: クライアントは Authorization ヘッダーに Bearer トークンを指定する必要がある。
```

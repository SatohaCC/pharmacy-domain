# 受入条件からテストを設計する

構造化された要求、受入条件、または Issue を入力とする。Issue の参照が必要なら [github-issue-workflow](../github-issue-workflow/SKILL.md) を使う。[qa-requirements-refiner](../qa-requirements-refiner/SKILL.md) の出力がある場合は、受入条件に加えてリスク、対象外、検証方法、未決事項も読む。

1. **設計できる範囲を確かめる。** 既存の受入条件 ID を保持する。ID がない条件は、参照元と対応付けた設計用の ID を付ける。対象範囲や合否を左右する提案・未決事項は、影響する条件と保留理由を記録し、確定している条件の設計を進める。
2. **テスト観点を選ぶ。** 受入条件ごとに確認する振る舞いとリスクを押さえ、必要なデータ、モック、実行環境を特定する。レビューや運用監視などで確認する条件は、その方法を記録する。
3. **テスト仕様に分解する。** 観点を独立して判定できる確認項目に分け、受入条件 ID と `TS-01` 形式の ID を対応付ける。同値分割・境界値、状態遷移、デシジョンテーブル、エラー推測などから、仕様とリスクに合う技法を選び、重複や未検証の組み合わせを確認する。
4. **実行できるケースにまとめる。** 一つの操作で関連する結果を確認でき、個別に合否を判定できる場合は、複数のテスト仕様を一つのケースにまとめてよい。ロジックや入力の境界は単体・統合テストを優先し、利用者経路や複数の境界をつないで初めて確認できる契約には E2E を使う。セットアップ、操作、期待結果の具体化には [test-design](../test-design/SKILL.md) の基準を使う。

## 出力

Markdown の見出しと ID をそろえ、受入条件から検証方法またはテストケースまでたどれるようにする。対応関係は表で示し、手順が長いケースはケース ID ごとに記述してよい。既存ケースのレビューでは、検証漏れ、重複、設計意図の不足を、該当する ID と影響を添えて示す。

- `## Test Requirements & Viewpoints` — 受入条件 ID、テスト観点、必要なデータ・環境、テストケース以外の検証方法、設計を保留した条件と理由。
- `## Test Specifications (Traceable Decomposition)` — テスト仕様 ID、対応する受入条件 ID、確認する条件と結果。小さな変更は前節に確認項目をまとめ、ケースから参照できる ID を残す。
- `## Test Cases (Execution & Automation Ready)` — `TC-01` 形式のケース ID、対応する受入条件 ID とテスト仕様 ID、設計意図（検出したい不具合や守るべき振る舞い）、テストレベル（単体、統合、E2E、手動）、前提・データ、操作・入力、観測可能な期待結果。ケースは独立して実行できるようにする。
- `## Exploratory Test Charter`（任意）— 手順を固定しない探索が適している場合に、対象リスクと探索の目的を記す。

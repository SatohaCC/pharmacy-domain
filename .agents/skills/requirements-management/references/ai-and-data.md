# AI・データの要件

参照章は第 5〜8 章、第 11 章 11.5 節。

## AI を要求管理の作業に使う

| 活動 | AI に渡す条件と確認する出力 |
| --- | --- |
| 聞き取り・獲得 | 前提と資料の範囲を提示し、質問案、発言や観測からの要求候補、少数でも重大な事象を抽出する。候補から原資料に戻れるようにする。 |
| 文書化・モデル作成 | 用語、対象範囲、既存様式、出力形式を与える。記述と根拠、推定箇所と未決事項を照合し、モデルの役割・例外・関係をレビューする。 |
| 過不足・矛盾の確認 | 要件間の重複、抜け、優先度、役割、出典が食い違う候補を出させる。判断が条件によって変わる場合は条件と確認先を記録する。 |
| 変更影響と再検証 | 変更内容と対象版、確認できるリンクを入力し、関連成果物とテストの候補を得る。実装・文書・テストの該当箇所を確認して採否を判断する。 |

資料の利用可否を確認し、原資料の該当箇所と照合する。頻度の集計と重大性の評価を別々に行い、現場・専門家が確認すべき例外を示す。AI が作った文書やモデルも版管理する。要求の採否、合意版の確定、変更の承認は担当する人が判断する。

複数の AI が作成やレビューを分担する場合は、会話の要約に加えて、要求 ID、候補文、根拠の箇所、出典の版、前提、検証候補、指摘を受け渡す。必要に応じて別の資料との照合やルール・スキーマ検査を組み合わせる。変更案は差分として残し、人が承認した版へ反映する。レビュー経緯が必要な場合は、利用したモデルやエージェントも記録する。

## システムや業務で AI を使う

AI を使う目的と適用範囲を確かめ、ルールベース、人による運用、既存機能を候補に含める。導入と運用の費用には、データ整備、利用料、評価・監視、人の確認、更新と再評価を含めて比較する。導入する場合は、以下のうち影響する条件を要件化する。

| 観点 | 仕様に含める情報 |
| --- | --- |
| 利用目的と責任 | 対象業務、許容・禁止用途、AI が担う範囲と人が判断する範囲、誰が確認・差し戻し・承認するか。 |
| 入出力と根拠 | 許容する入力・参照データ、出力形式、期待する品質、表示・保存する根拠、出力先。 |
| 判断できない場合 | 対象外、根拠不足、曖昧な入力、外部依存の停止などに対し、追加確認、保留、担当者への引き継ぎ、手動切替など、条件ごとの振る舞い。 |
| 社会的影響 | 直接利用する人と間接的に影響を受ける人を特定し、誤りや不利益の種類・分布・重大性を当事者や現場と確認する。影響に応じて説明、訂正・異議申立ての窓口、担当、対応記録を定める。 |
| 検証・監視・復旧 | 評価データ、指標と合格水準、監視・再評価・停止や復帰の条件、対応責任者、証拠。 |

プロンプトで担保する要件は、タスクの目的と入力範囲、出力形式、根拠の扱い、禁止や例外、確認方法に分解する。プロンプトと要件 ID、参照資料、評価ケース、版を結びつける。システム側の制御や人の確認が必要な条件は、それらの担当箇所と確認方法に割り当てる。

## 評価と継続的な確認

1. 対象業務、評価データの版と件数、評価手順、モデル・プロンプト・参照資料の版、実行条件を記録する。学習・調整に使ったデータと評価に用いるデータの混入を調べる。
2. 通常例、影響が大きい誤り、根拠不足、想定外入力を必要に応じて評価する。全体の指標に加え、重要分類や利用者群の成績、評価期間・件数・偏り、必要に応じて信頼区間や反復実行時のばらつきを示す。出力の許容範囲と、重大な誤りの上限を決める。自己申告などの確信度を判定に使う場合は、実際の誤りとの対応を検証する。
3. 評価ごとに、評価対象、指標、合格水準、根拠と採点方法、失敗時の行動を結びつける。合格水準や停止条件が未合意なら、決定する人と必要なデータを示す。候補値に根拠がある場合は添える。
4. 運用中の観測指標、頻度、しきい値、責任者、対応を定義する。性能低下、利用状況の変化、苦情や事故、モデル・プロンプト・参照データ・外部サービスの変更を、再評価に結びつける。変更前後は比較できるデータと評価条件を揃える。
5. 影響に応じて、利用制限、停止、手動運用、復帰の条件と、当時の判断を追える証跡を決める。高リスクな用途で継続的アシュアランスの根拠を管理するときは、満たすべき性質、その主張を支える証拠と前提、証拠が有効でなくなる条件をつなぐ。

運用を始める前に、影響の大きい機能について、誤出力、遅延、データ欠損、外部サービス停止から手動切替・復帰までを、業務シナリオで確認する。結果から不足する要件や監視条件を更新する。

例として、備品申請の分類を補助する場合、承認済み分類表の版に対象を限定する。「複数候補または分類不能なら、分類を確定せず担当者へ渡す」という要件に、類似したカテゴリ、分類表にない備品、担当者が修正する場合の評価ケースを結びつける。分類表の改定は、影響する分類・評価データ・担当者の手順を確認する起点にする。

## データの来歴と品質

- データの正本、取得元・方法・時期、取得時の目的と今回の用途、責任者、許諾・契約などの利用条件、対象期間、版、保存・削除条件を記録する。学習・評価・運用・参照など、用途が異なれば利用条件をそれぞれ確認する。
- 元データから加工、補正、匿名化、ラベル付け、学習・検証・テストへの分割、モデルや評価結果まで、関係する工程を版付きで追跡する。欠損、重複、陳腐化、データの混入を確認し、対象者、地域、言語、例外ケースの構成を実運用と照らし合わせる。ラベルを付ける場合は、基準と版、サンプルで確認した判断のばらつき、担当・確認者、変更時の再確認範囲を記録する。
- 参照文書は適用範囲、版、有効期間、優先関係を確認する。品質の低下、出典や利用条件の変更を検知したら、影響する学習、モデル、プロンプト、出力、評価や業務手順をたどる。運用データを再利用する場合は、利用条件と品質を確かめ、改善要求を観測した記録につなぐ。

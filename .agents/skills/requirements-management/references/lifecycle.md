# 要求管理の12工程とフィードバック

参照箇所は第 7 章 7.1〜7.2 節（本文 pp.52–55、PDF pp.68–71）と、第 11 章 11.3 節・図 21（本文 p.82、PDF p.98）。

## 12の標準的な工程

依頼に関係する工程を選び、今どの判断を進めているか、その根拠と次の工程に渡せる状態かを確かめる。工程名は第 7 章の流れに沿い、右列は案件に合わせて確認する項目を示す。途中から引き継ぐ場合は、前提として使う合意版、未決事項とその判断者、次の検証に必要な根拠を確認する。

| 工程 | 確認すること・次に渡すもの |
| --- | --- |
| 1. 目的・ミッションの確認 | 誰のどの課題を解くか、達成したい価値、対象範囲、成功基準。 |
| 2. ステークホルダーの特定 | 影響を受ける人、現場・運用担当、判断や合意を担う人、それぞれの制約や期待。AI を使う場合は、出力を使う人、確認する人、データ管理や事故対応を担う人も特定する。 |
| 3. 要求獲得 | 聞き取り、観察、既存資料やログが示す要求候補と、その発生源。 |
| 4. 要求分析 | 必要性、競合・依存、優先度、実現可能性、候補となる実現手段と判断理由。 |
| 5. 要求仕様化 | 条件、期待結果、適用範囲・例外、受入条件、確認方法。 |
| 6. モデリング | 業務、役割、状態、データ、評価の関係を示す図表と、対応する要件 ID。 |
| 7. 要求評価・妥当性確認 | 要件の一意性・検証可能性、業務シナリオに対する適合、関係者の共通理解、未決事項。 |
| 8. 要求ベースライン化 | 設計・開発・調達・評価の前提として合意した版、範囲、判断した人、保留事項。 |
| 9. 実装・調達・開発への接続 | 設計、実装、調達仕様や契約、テスト計画などと、元の要件との対応。 |
| 10. 運用・監視 | 利用状況、品質、問い合わせや監査の結果、監視指標、見直し条件と対応担当。 |
| 11. フィードバック・変更管理 | 変更の起点と理由、影響範囲、承認、関連する正本の更新、再検証結果。 |
| 12. 廃止・移行 | 利用者通知、データ・証跡の扱い、代替手段や契約終了、切替とその受入条件。 |

## 2つのフィードバック循環

第 7 章の工程間の手戻りと第 11 章の DevOps 型循環を、Skill で使う際の戻り先に沿って整理する。

1. **要求定義中の循環。** 分析・モデリング・妥当性確認（4〜7）で根拠不足、矛盾、例外の抜けが見つかったら、必要な要求獲得・分析・仕様化（3〜5）に戻る。目的や関係者の前提が崩れたときは 1〜2 に戻る。追加確認した根拠と修正した要件を結び、再評価してから合意した版を記録する。
2. **運用後の循環。** 監視や現場の声（10）から変更候補（11）を作り、変化した対象に応じて目的、要求、要件へ戻る。影響範囲と再検証項目を示し、合意した変更をベースラインと実現先（8〜9）へ反映する。リリース後の監視（10）で、狙った改善が得られたか確かめる。

聞き取りから進める場合は [要求獲得・仕様化・評価](elicitation-and-specification.md)、運用中の変更で戻る範囲を決める場合は [トレーサビリティと変更管理](traceability-and-change.md) を参照する。

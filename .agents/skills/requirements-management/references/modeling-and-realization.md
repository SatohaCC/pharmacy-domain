# モデリングと実現手段

参照章は第 3〜4 章、第 7 章 7.2.6 節・7.2.9 節、第 9〜10 章。

## 問いに合う方法を選ぶ

| 解きたい問い | 活用する考え方 |
| --- | --- |
| 利用者が抱える課題は何か | デザイン思考。観察と試作から、説明された要望の背景と利用時の障害を確かめる。 |
| 複数の組織や手段で、どの成果を達成するか | ミッションエンジニアリング。目的、成功の尺度、関係者、手段の役割を関連づける。 |
| 要望を合意・検証可能な条件にできるか | 要求工学。獲得、分析、仕様化、評価、変更管理を繰り返す。 |
| 人、業務、技術の境界を越えて目的を満たせるか | システムズエンジニアリング。構成要素とインターフェース、運用を含む全体を評価する。 |
| 要求や変更が構造・振る舞い・テストのどこに及ぶか | MBSE。必要なモデルと要求、評価の対応を管理する。 |
| 運用結果に応じて何を見直すか | アジャイルガバナンス。観測する指標、判断者、適用を続ける条件、見直しの周期を決める。 |

観察・試作で分かった課題や、ミッションから得た成功指標は、要求候補とその根拠に反映する。システム全体を検討して見つけた役割の抜けや連携条件は、要件と確認方法に落とす。運用で目的やリスクの前提が変わったら、関係者と成功基準を見直す。

## 可視化する

| 解釈をそろえたい点 | モデルと含める情報 |
| --- | --- |
| 作業、引き継ぎ、承認、例外 | 業務フローや BPMN。開始と終了、役割、判断、差し戻し、手動での復旧を示す。 |
| 状態ごとの操作、禁止される状態 | 状態遷移図または遷移表。現在状態、操作主体、イベント、条件、次状態、拒否時の挙動を書く。 |
| 条件の組み合わせや優先順位 | 決定表。適用条件、例外が重なった場合の優先順位、結果を確認する。 |
| データの意味・関係・外部連携 | データモデルや API 定義。正本、項目・制約、入出力、エラー、版の関係を示す。 |
| 事業目的からサービスやシステムへのつながり | 業務とシステムの構成図。複数の領域をまたぐ場合は ArchiMate や SysML なども検討する。 |

目的を一つ選び、重要な経路・データから始める。図や表の要素に要件 ID を対応させ、根拠、実装、テストへつなぐ。読める文章には、関係者が意味をそろえるための図表・用語定義を添える。機械で抽出・検索する場合は安定した ID と属性を付ける。整合性確認や影響分析に使う場合は、モデル要素の関係の意味（実現する、依存する、検証するなど）も定義する。引き継ぎの待ち時間やボトルネックが判断に効く場合は、モデル上で経路をたどり、条件を変えた場合の差を確かめる。例えば「却下済みから承認済みへ遷移しない」のような重要条件は、状態表と検証ケースを対応させる。安全性が高く求められ、状態や並行操作の組み合わせを尽くす必要がある場合は、検証したい性質とモデルの前提を明記して形式手法も検討する。結果と前提を要件 ID、設計、テストや監視の証跡に結びつける。

## 実現手段と部品を選ぶ

業務上の能力と境界をモデルから取り出し、既存機能、追加開発、OSS、商用製品、SaaS、外部 API などの選択肢を評価する。採用候補ごとに、対応する要件 ID、適合を示す根拠、差分を埋める手段、運用・移行までの費用、残るリスクを示す。

- **単体の適合**を確認する。入出力・エラー・互換性と版、性能・可用性・データの取扱い、監視、障害連絡、データ返却・削除の条件を、該当する要件に照らす。
- **インターフェースの共通部分**を明示する。入出力の意味、認証・権限、エラー時の処理、版、ログと責任分界をそろえ、接続先を交換した場合に再検証する条件を決める。
- **組み合わせ全体の適合**を確認する。依存箇所も含めた性能、障害時の切り分けと代替手段、アクセス権や監査、統合テストと運用責任を定める。部品の細分化による利点と、増える連携・保守の負担を比較する。
- **実現と契約へ引き継ぐ。** 調達条件、部品の責任範囲、受入条件に要件 ID を対応させる。版変更・サービス終了時の通知、置き換え先への移行、データの出力・返却・削除を確認する。

## 複数の地域・組織にまたがる場合

共通の目的・原則から、全体で合わせるデータ定義、識別子、連携仕様、品質・証跡と、地域ごとに変わる制度、データ越境、言語、承認・運用を整理する。各要件がグループ共通、地域、国・拠点・事業、期限付き例外のどこに適用されるかを示す。差分には理由、適用範囲、責任者、見直し時期、共通仕様との関係を記録する。重要な用語は言語間の対応と正本となる言語・版を記録し、曖昧な品質条件は測定・報告方法に具体化して、現地の担当者と解釈を確認する。

サプライチェーンの接続では、参加条件、データの受け渡し、変更の通知、取引先に依存する責任と代替条件を具体化する。M&A では、調査時に対象組織と共通の基準との差を確認する。統合計画では、現行の業務・データの正本・委託や制度の条件を棚卸しし、統合対象と地域固有の残存条件、移行の受入基準を合意する。運用後は問い合わせ、監査指摘、制度変更などを共通要件と地域の差分の両方に戻す。

# React Hooks パターン（Custom Hook 設計）

## 基本原則
状態管理・外部同期・関連する操作群（stateful logic）は Custom Hook（`use*` 関数）に切り出すことで、HOC や Render Props、不要なラッパーコンポーネントでツリーを深くすることなく再利用・整理できる。一方で、単なる純粋関数で足りる計算や1箇所だけの単純な状態まで機械的に Hook 化しない。

## Hook を切り出す判断基準

まず対象のロジックが「React の状態・ライフサイクル・外部同期に依存するか」と「抽出によって見通しや再利用性が上がるか」を確認する。

| ケース | 判断 | 理由・注意点 |
|---|---|---|
| 複数のコンポーネントで同じ状態遷移や外部購読を使う | Custom Hook を作成 | コンポーネント階層を増やさずロジックだけを共有できる |
| 1つのコンポーネント内で独立した関心事（状態＋操作群）が肥大化 | 責務単位で Custom Hook に抽出 | 読みやすさは上がるが、過度な細分化で処理の流れを追いにくくしない |
| React の state / ref / effect を使わない純粋な変換・計算 | 通常の関数（util）にする | `use` を付けると Hooks の制約だけが増えて利益がない |
| 1箇所でしか使わない単純な `useState` 1〜2個 | コンポーネント内に残す | 呼び出し元と定義を行き来する間接参照のコストが上回る |

## 実装の指針

- **命名と最小限の契約**: Custom Hook は必ず `use` で始め、呼び出し側が必要とする値と意図を表す操作関数だけを返す。生の `setState` や内部の `ref` を無条件に丸ごと返してカプセル化を壊さない。
- **呼び出しごとに状態は独立**: 同じ Custom Hook を2箇所で呼んでも **state は共有されない**。コンポーネント間で状態を共有したい場合は、親へのリフトアップ、Context、外部ストア、キャッシュ（TanStack Query 等）を使う。
- **Rules of Hooks を守る**: Hook はコンポーネントまたは他の Custom Hook のトップレベルでのみ呼び出し、条件分岐・ループ・イベントハンドラ内で呼ばない。
- **不要な `useEffect` を隠さない**: Custom Hook の中に切り出しても、派生値の同期やイベント起因の処理を `useEffect` に書かない。外部リソース（WebSocket・MediaStream・タイマー・イベントリスナ等）の同期に使う場合は、必ずクリーンアップで解除し、複数箇所で呼ばれたときの二重購読・二重接続に注意する。
- **既存のデータ取得・基盤を尊重する**: 記事の例にあるような素朴な `fetch` + `useEffect` を新規に書かず、プロジェクトが採用しているデータ取得基盤（例: `@tanstack/react-query`）や状態管理方針に従う。
- **表示境界との併用**: Hook でロジックを抽出しても、その Hook を直接呼ぶコンポーネントは Hook の外部依存を引き受ける。Storybook 等で外部依存なしに見た目を確認したい場合は、`react-presentational-container` の方針に沿って props 境界を残す。
- このプロジェクトの `frontend/` を変更するときは、`frontend/AGENTS.md` を含む適用ルールを優先する。

## 検証とレビュー

Custom Hook を変更・追加した場合は、初期状態、操作による状態遷移、異常系・クリーンアップ（解除・再接続など）が期待通り動くかを確認する。呼び出し側のコンポーネントと合わせた結合動作も必要に応じて検証する。

レビューでは「Custom Hook 化されていない」こと自体を指摘せず、重複・肥大化・責務の混在という具体的な課題が解決されるか、逆に見通しが悪化していないかを確認する。

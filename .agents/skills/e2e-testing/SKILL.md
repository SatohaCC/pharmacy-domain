# E2Eテスト

## 1. 検出したい不具合からテストを選ぶ

変更の受入条件、影響を受ける利用者の操作と境界、既存テストを確認する。各ケースに「前提 → 操作 → 観測結果」を置き、そのケースが検出する不具合を説明できるようにする。AAAの共通作法は [test-design](../test-design/SKILL.md) を参照する。

| 確かめたいこと | 選ぶテスト |
| --- | --- |
| UI・アプリ・API・永続化などの結合を通り、重要な利用者の目的を達成できる | 実際の境界を通すE2E。たとえば保存して再表示しても値が残る |
| APIの異常応答を受けた画面の回復、部品の操作・フォーカス・描画 | 境界を制御したブラウザ統合テスト、またはStorybookでのブラウザテスト。使ったモックを記録する |
| 計算、入力の境界値、権限ポリシーの組み合わせ | 単体テストやAPI統合テストで表形式に網羅する。結合に固有のリスクがある代表例をE2Eに置く |
| 変更頻度の高い画面の受入確認、操作経路の探索、単発の再現 | 自然言語シナリオでブラウザ実行。反復して検出したい重要な回帰はPlaywright Testに固定する |

コンポーネントを組み合わせてページ全体を操作するテストは、手順や保守の負担がE2Eに近づく。重複があれば、実APIや永続化を通す価値と、応答を制御して画面の分岐を検証する価値を比べて配置を決める。拒否を検証するときは、エラーや無効状態に加えて、必要に応じて保存・送信などの副作用が残っていないことを確認する。状態遷移の組み合わせが主なリスクで仕様モデルがある場合は、固定シナリオにモデルから生成する経路を加える。

期待値は実行前に仕様、決定表、手計算した例、または独立した参照実装から定める。同じ実装の出力を照合に使う場合、確認できるのは画面との一致まで。期待値の根拠が欠けている箇所は判定を保留する。

## 2. 前提を再現できるようにする

- **API・fixtureで準備する。** 履歴やお気に入り登録など、検証対象の操作に不要な手順はセットアップに移す。対象の操作は利用者と同じ入口から行う。Feature flag、時計、外部サービスなど結果を変える条件は、対象境界を保てる範囲で固定する。
- **変更するデータを隔離する。** BrowserContextに加えてDB上の状態を考える。読み取り専用データは共有できる。更新するレコードはテスト単位、必要なアカウントやテナントはテストまたはworker単位で割り当てる。同じ環境を複数のCI実行やshardが共有する場合は実行単位の名前空間も持たせる。
- **再試行できるようにする。** 準備を冪等にするか試行ごとに専用データを作る。失敗時もfixtureの後処理などで自分が作ったデータを回収する。テスト用アカウントの履歴を初期化する場合、そのアカウントを同時に使うケースがないことを確認する。
- **並列化の前に測る。** 対象ケースを単独で繰り返し、通常の並列実行でも確認する。並列時だけ落ちる場合は、データ競合、環境の共有、依存サービスの負荷から調べる。準備・操作・待機・起動のどこに時間を使っているか測ってからworkerやshardを調整する。

## 3. Playwrightで検証し、運用する

- 操作対象は役割とアクセシブルな名前で探し、必要に応じて安定したテストIDを使う。アサーションはPlaywrightの再試行付き `expect` を使い、意味のある画面状態や完了シグナルを待つ。応答待ちが必要なら操作の前に登録し、その後に利用者が観測できる結果も検証する。
- テストにはシナリオの意図と期待結果を残す。長いフローは意味のある単位で `test.step` を使う。重複が増えたら変更理由に合わせて、環境設定（URL等）、テスト（シナリオと検証）、Action（複数操作の業務手順）、Page Object（ロケーターと基本操作）を分け、fixtureで接続する。単純なフローはspec内の記述で十分。抽象化した後もロケーターを使った再試行付きアサーションができるようにする。
- 回帰修正では可能な範囲で、修正前に狙ったアサーションで失敗し、修正後に通ることを確認する。初期状態のまま成功するケースでは、操作前後の差や再表示後の状態を確認する。失敗時はtrace・レポートから最初の失敗箇所、DOM、ネットワークを照合する。再試行で通ったケースはflakyとして扱い、初回失敗も残す。
- ケース数が増えて追跡が難しくなったら、受入条件・画面やAPIとシナリオIDを対応づける。CIで参照切れ、未対応項目、実テストの有無を照合できる。アサーションの妥当性は仕様と突き合わせてレビューする。
- 機械判定でき、繰り返し起きる逸脱は既存のlintやCIで扱う。たとえば固定sleepや常設の `test.only` を検出する。適用範囲、例外、既存ケースの移行を定め、新設ルールの適用状況と古いヘルパー・文書を定期的に見直す。

## このテンプレートでの実行

ルートから実行する。設定、ポート、レポートの場所は [README](../../../README.md) と [Playwright設定](../../../frontend/playwright.config.ts) を確認する。

| 用途 | コマンド |
| --- | --- |
| Next.js と FastAPI を起動し、ChromiumでE2Eを実行 | `pnpm test:e2e` |
| 対象specを絞って反復する例 | `pnpm test:e2e health.spec.ts --workers=1 --repeat-each=3` |
| Storybookを静的ビルドし、部品を実ブラウザで検証 | `pnpm test:storybook` |

既存の [health.spec.ts](../../../frontend/e2e/health.spec.ts) には実バックエンドへの疎通確認と、`page.route` で失敗・不正応答を作るブラウザ統合テストがある。新しいケースの位置や命名を決める際も、実際に通した境界で説明する。

実行結果には対象、コマンドまたはシナリオID、環境、ブラウザ、結果、使ったモック、失敗の証跡を残す。未実行・ブロック・再試行後のみ成功も明示する。

- 自然言語でブラウザを操作する場合は [自然言語シナリオの実行手順](references/agent-browser-testing.md) を読む。

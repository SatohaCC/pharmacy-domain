# このリポジトリの検証手順

変更の影響を観測できる最小の検証から始める。回帰テストを追加する場合は、可能なら修正前に元の症状に対応するアサーションが失敗することを確かめる。検証の入口はルートの `package.json` と [README](../../../../README.md) を参照する。

| 確認する契約 | 既存の入口 |
| --- | --- |
| FastAPI の HTTP 応答 | `pnpm test:backend`。絞る場合は `pnpm -C backend exec python -B -m pytest` に対象テストを渡す。 |
| React コンポーネントの操作と表示 | `pnpm test:frontend`。ブラウザ固有の動作や StyleX の実描画が対象なら `pnpm test:storybook` を使う。 |
| ブラウザから API までの接続 | `pnpm test:e2e`。サンプル画面を確認する場合は `pnpm test:e2e health.spec.ts`。 |
| 開発スクリプトの動作 | `pnpm test:scripts`。 |

## ブラウザから API までの確認

1. E2E は Playwright が必要なサーバーを起動する。ローカルの 3000 / 8000 番ポートに起動済みのサーバーがある場合は、対象ワークツリーのものか確認する。別のインスタンスなら再利用を避ける。
2. [サンプル画面の E2E](../../../../frontend/e2e/health.spec.ts) では `/` を開き、「状態を更新」を押したときに `/api/health` の成功応答と `ok (template-backend)` の表示を確認する。障害と復帰を模擬するケースは、実 API の結合確認と区別して報告する。
3. 別の画面を手動で確認する場合は `pnpm dev` で立ち上げ、変更した実際の利用者経路を操作する。ブラウザで発生する症状は画面で再現し、通信の結果と画面の表示を確かめる。保存を伴う変更では保存結果も確認する。手動で立ち上げたサーバーは、自分のセッションで起動したものを終了する。

完了の証拠には、対象テスト名と結果、または実行した操作と観測結果を残す。描画や配置が合格条件なら、必要に応じてスクリーンショットやブラウザでの計測値を添える。

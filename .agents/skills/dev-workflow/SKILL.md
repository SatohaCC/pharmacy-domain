# 開発ワークフロー

## 着手から PR 提出まで

1. **機能追加・変更の要求を分析する。** [requirements-management](../requirements-management/SKILL.md) を使い、既存仕様や依頼をもとに、目的、対象の利用者と範囲、制約、受入条件、未決事項を整理する。既存の合意を使い、実装範囲や受入条件を左右する未決事項は、影響する作業の着手前に確認する。
2. **Issue を用意し、作業単位を決める。** [github-issue-workflow](../github-issue-workflow/SKILL.md) の分割基準を着手前に適用する。既存 Issue を含め、各作業単位を個別に検証・レビューできるか確認する。作業が一単位なら Issue 一件を再利用または起票する。複数なら親 Issue に全体の目的と受入条件を記し、各サブ Issue を再利用または起票して親に紐付ける。正本となる仕様があれば参照先を付ける。
3. **作業単位ごとに調査・実装・検証する。** 作業ブランチ一つに、対象の Issue またはサブ Issue 一件を対応させる。実装前に [AGENTS.md](../../../AGENTS.md) から変更対象に該当する規約を読み、対象ディレクトリに `AGENTS.md` があれば併せて確認する。担当の完了条件に沿って進める。作業中に独立して検証・レビューできる別の成果が見つかった場合は、追加の変更を取り込む前に作業単位を見直す。
4. **コミット前レビューを行う。** [git-commit](../git-commit/SKILL.md) に対象 Issue、担当する受入条件、検証結果と未確認の範囲を渡す。コミットと push にはリポジトリの Git のルールを適用する。
5. **作業単位ごとに PR を提出する。** 分割した場合はサブ Issue 一件につき PR を一件ずつ提出する。作業が一単位なら Issue 一件と PR 一件で完結させる。同じ作業単位のオープンな PR があれば更新する。
   - 複数のサブ Issue がある場合は、全作業の完了を待たず、各単位の実装と検証が完了するたびに、明示的な承認を得て push・PR 提出へ進む。
   - 提出前にベースブランチとの差分を確認し、担当 Issue の成果物と検証だけを含める。他のサブ Issue の差分が混ざっていたら、担当ブランチへ分ける。サブ Issue や Stacked PR に分割する場合でも、各 PR が単独で既定ブランチにマージされた時点で既存ルートや既存機能の契約が壊れない状態を保つ。
   - PR のベースは原則として既定ブランチとする。本文に担当 Issue、変更内容、受入条件ごとの検証結果と未確認の範囲を記す。既定ブランチ向けの PR は `Closes #番号` で担当 Issue に紐付ける。親 Issue は関連先として記載し、全体の完了は親 Issue で判定する。
   - 未マージの先行 PR に依存する場合は、そのブランチをベースとする PR を使ってよい。本文に先行 PR と担当 Issue を明記する。先行 PR のマージ後にベースを既定ブランチに切り替え、差分と `Closes #番号` による紐付けを確認する。既存 PR 本文を更新する際、`gh pr edit` が GraphQL エラー（旧 Projects `projectCards` 廃止等）で失敗する場合は REST API（`gh api --method PATCH repos/<owner>/<repo>/pulls/<number> -F body=@<file>`）で更新し、コマンド成功と本文反映を確認する。
   - Stacked PR の先行ブランチに修正が入った場合は、force-push を避け、先行ブランチを後続ブランチにマージして同期する。後続 PR のベースに対する差分が担当範囲だけであることを確認し、影響する検証を再実行してから承認済みの後続ブランチを push する。
   - PR 作成後に対象 Issue・ベース・差分を確認する。PR 作成後と PR ブランチへの追加 push 後は、そのコミットの CI を `gh pr checks <番号> --watch` などで確認する。失敗または実行待ちのチェックがあれば、対応が必要なものと結果を記録する。

## 合意済みの要求が変わるとき

作業中に、合意済みの期待動作・対象範囲・受入条件の変更が必要と分かったら、影響する作業を進める前に [requirements-management の変更影響分析](../requirements-management/SKILL.md) を使う。影響を受ける要求・Issue・テストを特定し、変更の理由と判断を記録する。変更の合意後に正本を更新し、関連する Issue の作業範囲・受入条件、該当するテスト、作成済みの PR の説明と検証結果に反映する。合意済みの期待動作を実装が満たしていない場合は、現行の受入条件で不具合を追う。

## 作業に合わせた検証

依頼と制約から、合否を判定できる条件を決める。主目的に合う手順を選び、対象の入口から関係する処理とテストをたどる。

| 目的 | 手順 |
| --- | --- |
| 調査 | 値の生成・保持・参照をたどり、失敗がどこに波及するかを調べる。確認できた事実と仮説を報告する。 |
| バグ修正 | 可能なら現行コードで再現し、観測結果で原因を絞る。原因箇所を修正し、同じ入口と条件で再実行する。環境エラーは再現の証拠に含めない。 |
| 機能追加・変更 | 影響する利用者経路と合格条件を決め、実装後にその経路を通す。障害時の挙動が契約に含まれるなら、そこも確かめる。 |
| リファクタリング | 維持すべき公開契約を特定し、変更前後で同じ検証を通す。 |

既存の規約と依頼されたレビュー手順に従う。モジュール間の契約を変える場合は、受け渡すデータの型と各モジュールの責務を先に決める。関連箇所から確認範囲を広げ、テスト出力は失敗箇所と結果の要約を読む。既存の検証を優先し、再現や回帰検出に不足があれば補う。UI・API・スクリプトの実行経路に合う検証を選ぶときは [検証手順](references/verification.md) を読む。

テストを設計・追加・修正するときは [test-design](../test-design/SKILL.md) を使い、対象 Issue の受入条件から検証ケースを選ぶ。サブ Issue では親 Issue や正本を参照し、担当範囲の条件を使う。受入条件の検証に、ブラウザから API や保存先までなど、利用者経路がまたぐ境界を実際に通す必要がある場合は [e2e-testing](../e2e-testing/SKILL.md) を使う。

結果は受入条件ごとに、実行した操作またはコマンド、観測結果、未確認の範囲とその理由を必要な分だけ示す。作業を引き継ぐ場合は、依頼と制約、確認済みの証拠、次の一手を残す。提出結果には対象 Issue と対応する PR の URL をペアで示す。分割した場合は、親 Issue の URL も添える。
